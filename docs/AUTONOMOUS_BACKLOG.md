## AUTO-014 — Skimmer Premium Pass (real-geometry housing variants)
- Problem: the skimmer had a single moulded housing shape regardless of any user choice -- no way to differentiate the product visually beyond the existing 3-colour ABS finish swap, per the "Visible Premium Realism" phase's Phase A directive.
- Solution: added a `SkimmerTypeId` ("standard" | "slim" | "highWaterline" | "flush") and a "Tipo skimmer" selector (`PoolSystemStep.tsx`, next to the existing "Finitura skimmer" swatches) driving 4 dimensionally distinct housing assemblies in `Skimmers.tsx`:
  - **Standard Refined** -- unchanged, previously-shipped moulded raised-bevel frame (48x19.5cm), kept as the reference/baseline.
  - **Slim / Modern** -- ~half the bar thickness/width, thinner protrusion (0.018 vs 0.035), wider throat-to-frame ratio, no accent trims.
  - **High-Waterline** -- short housing (0.14m vs 0.195m native) set high with a much smaller `verticalDrop` (0.09 vs 0.16), water plane pushed to the top of the throat instead of mid-throat.
  - **Architectural Flush** -- near-flush bars (0.008 protrusion vs 0.035), sharp minimal bevel, plus a dedicated dark shadow-gap groove ring recessed just outside the plate (the directive's explicit "shadow gaps" requirement) instead of a raised frame.
  Also extended `SkimmerFinishId` with a `steel` (satin AISI-316-style) finish -- `metalness: 0.9`, `clearcoat: 0` (no fake-chrome lacquer over bare metal), higher IOR -- alongside the existing white/graphite/sand moulded-ABS finishes (all `metalness: 0`).
- Files: `src/lib/pool/types.ts`, `src/lib/pool/config.ts` (`SKIMMER_TYPES`, extended `SKIMMER_FINISHES`), `src/lib/pool/context.ts`/`store.tsx` (`setSkimmerType`), `src/lib/pool/materials.ts` (`ResolvedMaterials.skimmer.{type,metalness}`), `src/components/pool/three/Skimmers.tsx` (rewritten: `StandardSkimmerAssembly` extracted verbatim + 3 new assemblies), `src/components/pool/three/PoolScene.tsx` (passes `variant`/`metalness` through), `src/configurator/steps/pool-system/PoolSystemStep.tsx` (new selector), `src/lib/render-pipeline/serialize.ts` (updated `resolveMaterials` call site only -- render-pipeline schema/Blender contract intentionally untouched, out of scope for this phase).
- Risk: Low-medium -- purely additive types/config/UI; `Skimmers.tsx`'s Standard path is numerically unchanged from the previously-validated geometry (new variants are separate functions, not a shared formula engine, to keep zero regression risk on Standard). `test:geometry` doesn't exercise this file (SkimmerPlan/camera math only) so no coupling risk there.
- Acceptance: all 4 variants dimensionally distinct (verified below), sit correctly against the wall (no floating parts observed), no z-fighting/artifacts in close-up, correct waterline relationship per variant (High-Waterline's opening reads visibly closer to the coping/shorter than the others).
- Status: COMPLETE. Verified `tsc --noEmit`, `test:geometry` (108/108), `lint` (86 problems, baseline unchanged after `--fix` reflow), `build`, plus an ad hoc Playwright close-up smoke test (zoomed OrbitControls view of the Pool System step's skimmer wall, real macOS Chromium -- not committed to `scripts/visual-audit.mjs`, which is sandbox-tuned per AUO-009's header comment) confirming all 4 variants render distinctly, no console errors, and the `steel` finish renders a credible satin-metal look (no black-hole/missing-envmap artifact).
- Follow-up: no dedicated skimmer close-up baseline exists yet in `test-baselines/visual/` -- add one (or four, one per variant) to `scripts/visual-audit.mjs`'s `REFERENCES` next time this file is touched, per `AUTO-009`'s "add a reference alongside the change that touches it" policy (not done this session to keep this pass's footprint minimal per the low-consumption directive).
